# Publishing the easypdf.surf site

The site lives in `site/` and is made of static files: no server and no
database. The main page is in **English** (`/`) and the Spanish version hangs
off `/es/`; both are generated by the same script so they cannot drift apart:

```bash
python tools/build_site.py     # writes site/index.html, site/es/index.html,
                               # robots.txt and sitemap.xml
```

## The browser tools

`/tools/` (and `/es/tools/`) holds six small tools that run entirely in the
visitor's browser: merge, split, rotate and reorder, delete pages, images to
PDF and PDF to image. They are generated by `tools/build_tools.py`, which
`build_site.py` calls, so `python tools/build_site.py` rebuilds everything.

A few things worth knowing before changing them:

- **Nothing is uploaded, and that has to stay true.** The two libraries
  (`pdf-lib` and `pdf.js`) are vendored under `site/tools/vendor/` rather than
  pulled from a CDN, so no third party ever sees a document — and there is a
  test that fails if a page starts loading a script from somewhere else.
- **One service worker for the whole site**, at `/sw.js`. Its scope is `/`, so
  it covers `/es/` and `/tools/` as well. There used to be one per language
  and each cleaned up "every cache that is not mine", which meant they took
  turns wiping each other; there is a test for that now.
- **Bumping the cache version.** After changing `app.js` or `app.css`, raise
  the version in `site/sw.js` (`PREFIX + "v1"`) so returning visitors get the
  new files instead of the cached ones.
- `render.yaml` serves `/tools/vendor/*` as immutable for a year and `/sw.js`
  with `no-cache`, which is what makes an update actually arrive.
- **One manifest**, at `/manifest.webmanifest`, scope `/`. Installing from
  anywhere on the site gives the landing page and the tools together.

## The numbers on the front page

- **Downloads**: GitHub counts them on the files of every *release*. The page
  adds up the `download_count` of every file with one request to GitHub's public
  API and keeps the result in the browser for an hour. There have to be numbers
  to show, which means a release must have been published: that is done with the
  *Publish release* workflow in the Actions tab. This is why **the site's
  download buttons point at the release files** and not at the repository's
  `raw` ones: nobody counts those.
- **Visits today and in total**: a public, cookie-free counter from
  [counterapi.dev](https://counterapi.dev). It adds one per browser per day,
  stores nothing about who visits, and if the service fails the number simply
  does not appear (a made-up figure is never shown).

If one day you want real analytics (most visited pages, referrers, which country
people come from), change `VISITS_API` in `tools/build_site.py` for
[GoatCounter](https://www.goatcounter.com) or [Plausible](https://plausible.io):
both are cookie-free and have a free plan for open projects.

## Render (the official option)

1. In Render: **New → Blueprint** and pick this repository. Render reads
   `render.yaml` and creates the static site pointing at `site/`.
   (It can also be done by hand with **New → Static Site**: an empty *Build
   command* and `site` as the *Publish directory*.)
2. Every `git push` to `main` redeploys.
3. **Your own domain**: Settings → *Custom Domains* → add `easypdf.surf` and
   `www.easypdf.surf`. Render shows the exact DNS records to create at the
   domain provider: usually an **A** record for the bare domain pointing at the
   IP Render gives, and a **CNAME** for `www` towards
   `<site-name>.onrender.com`.
4. Render issues the HTTPS certificate on its own once the DNS points at them
   (it can take a few minutes).

> The installers are not copied to the site: the download links point at the
> files from `build/` on GitHub, so the site weighs a few hundred kB.

## GitHub Pages (mirror)

The `.github/workflows/pages.yml` workflow copies `site/` to the `gh-pages`
branch on every change. Turning Pages on for that branch leaves a mirror of the
site at `https://mefardales.github.io/easypdf/`. It carries no `CNAME` file on
purpose: the domain is handled by Render.

## SEO

What the page already carries:

- A different title and description per language, with the words people actually
  search for ("free pdf reader", "lector de PDF gratis", "annotate PDF").
- `canonical` and `hreflang` (en, es and `x-default` pointing at English) on
  both pages.
- JSON-LD structured data: `SoftwareApplication` (with price 0) and `FAQPage`
  with the frequently asked questions.
- Open Graph and Twitter Card tags with the screenshot, so the link looks right
  when shared.
- `robots.txt` and `sitemap.xml` with both URLs.
- Semantic HTML, a single `h1`, alt text on the images and a skip-to-content
  link.

- A `lastmod` in the sitemap that only moves when the page really changed.
  It used to be rebuilt as "today" on every run; search engines learn to
  ignore a date that is always now, and it made a rebuild differ from the
  committed site for no reason. The hashes live in `site/.lastmod.json`.
- `BreadcrumbList` on every tool page, an `ItemList` of the tools on the hub,
  `max-image-preview:large`, `og:image` dimensions and alt text, and the
  screenshot served as WebP with a PNG fallback.

After the first deployment it is worth registering the domain with
[Google Search Console](https://search.google.com/search-console) and submitting
`https://easypdf.surf/sitemap.xml`.
